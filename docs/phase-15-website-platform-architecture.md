# Phase 15 Website Platform Architecture

## Status and scope

This document defines the production direction for the KS OS managed website
platform. Phase 15.0 establishes the architecture, Phase 15.1 establishes the
site domain model and page entitlements, and Phase 15.2 establishes the native
booking conversion contract. Phases 15.3–15.13 are documented extension points
only.

The platform creates responsive, accessible, SEO-focused and
booking-conversion-focused websites for appointment-led KS OS tenants. It is not
a DIY website builder, general-purpose CMS, client-controlled page builder, or
arbitrary AI site generator. Every site has one primary conversion objective:
`BOOK_APPOINTMENT`.

## Control model and product boundaries

Agency users own template ingestion and classification, architecture, page
planning, structured generation, editing, imagery, SEO, quality review,
publishing, rollback, domains, monthly page opportunities, and booking CTA
configuration.

Business clients can view signed previews, review factual information, approve
or reject factual content, comment, request managed changes, and view simplified
status and analytics. They cannot edit content or layout, select templates,
change metadata, publish, delete pages, configure domains, upload scripts,
change booking destinations, or access infrastructure credentials or source
code.

The API must enforce these boundaries. Hiding client controls in the web
application is not authorization.

## Production topology

### `apps/web`

- Agency Site Studio.
- Client factual preview and approval.
- No client editing or publication controls.

### `apps/api`

- Authentication and agency capabilities.
- Tenant-scoped site records, versions, pages, sections, assets and blueprints.
- Approval and managed change-request records.
- Entitlement calculation.
- Publication orchestration and job creation in future phases.
- Append-only platform auditing for agency mutations.

### Future `apps/sites`

- One public multi-tenant renderer, not one repository or application per
  client.
- Resolve a verified hostname or signed preview context to exactly one tenant
  and site.
- Render immutable published snapshots.
- Provide fallback subdomains, custom domains, canonical metadata, structured
  data, sitemap output and cache invalidation.
- Mount or link `/book` to the same native KS OS booking journey used by the
  existing `/book/:subdomain` fallback.

### Future `apps/site-worker`

- Long-running PostgreSQL-leased work.
- Template analysis, structured AI generation, image optimisation, audits,
  publishing and domain-verification jobs.
- Idempotent execution, bounded retries and backoff.
- No arbitrary executable code generated by AI or supplied by users.

`apps/sites` and `apps/site-worker` are not scaffolded in Phase 15.0 because no
runtime implementation is required yet.

## Site and content model

A tenant may own one managed website in the initial foundation. The site is the
stable identity and lifecycle record. Its versions contain content state. Pages
belong to versions; ordered sections belong to pages. Assets are tenant-owned
records referenced by structured content. Blueprints and blueprint pages
capture the approved page plan before or alongside draft generation.

Content is stored as structured, versioned database records. Generated HTML is
not committed to a per-client repository. Stable lifecycle and
security-sensitive attributes use typed relational columns. JSON is reserved
for bounded structured content, design tokens, source metadata and future
snapshot manifests where a fixed relational shape is inappropriate. JSON must
never contain credentials or executable JavaScript.

## Version immutability, publication and rollback

- `DRAFT` versions may be edited by an authorised agency user.
- Review transitions produce `INTERNAL_REVIEW`, then optionally
  `CLIENT_REVIEW`, then `APPROVED`.
- A published version is immutable. Database and service-level guards reject
  page, section or version mutation once its status is `PUBLISHED` or its
  publication timestamp is set.
- Publishing will create or select an immutable snapshot and atomically point
  the site at the published version. Phase 15.1 stores that pointer and
  publication history; provider automation is deferred.
- A later publication supersedes but never deletes the prior published version.
- Rollback selects a previous valid published version and records a new
  publication event. It does not mutate historical content.
- Published versions must never be hard-deleted.

Site lifecycle:

`SETUP_REQUIRED → DRAFT → GENERATING → INTERNAL_REVIEW → CLIENT_REVIEW → APPROVED → PUBLISHING → LIVE`

Failure, suspension and terminal states are `PUBLISH_FAILED`, `SUSPENDED` and
`ARCHIVED`. Version lifecycle values are defined independently.

Approvals are factual review records and do not grant publication authority.
Client comments and managed change requests become agency work; they do not
mutate site content directly.

## Multi-tenant and security rules

- Every tenant-owned site record carries `tenant_id`, including child records
  whose parent already implies tenancy.
- Service queries constrain both public reference and tenant ID. A reference
  from Tenant A cannot read or mutate Tenant B.
- Browser requests never choose an internal tenant ID for public rendering or
  booking. Future public resolution begins from a verified hostname or signed
  preview context.
- Public-facing records use public references. Internal primary keys remain
  server-side.
- Site control-plane tables are API-only: RLS is enabled, `anon` and
  `authenticated` table access is revoked, and the backend service role receives
  only the access it needs.
- Agency endpoints require explicit `sites.*` capabilities. Tenant roles do not
  receive those capabilities.
- Agency mutations write redacted platform audit events. Generated content,
  private customer data, credentials and tokens are not copied into audit
  metadata.
- Domain records store status, hostnames and safe verification metadata, never
  provider credentials.
- AI and client content cannot supply executable scripts, arbitrary primary CTA
  URLs, internal IDs or infrastructure configuration.

## Page entitlements

The active immutable plan assignment is the commercial source of truth.
Website limits are plan entitlements, not browser-supplied counts:

| Plan | Initial marketing pages | Monthly opportunities |
| --- | ---: | ---: |
| Core | 10 | 1 |
| Growth | 20 | 2 |
| Scale | 30 | 3 |

`BOOKING` is a functional system route and does not consume marketing-page
allowance. Required legal or functional pages can be marked non-consuming.
Tenants may launch with fewer than their allowance when source information is
incomplete. Unused allowance is an agency action item, not a reason to generate
thin pages.

Initial allowance measures current non-archived marketing pages in the site
plan. Monthly allowance measures completed monthly opportunities in the
applicable UTC calendar month. Page creation is checked transactionally on the
server.

## Template and design sources

Future template intelligence accepts:

- `ENVATO_HTML`: licensed source packages, with purchase and licence records
  retained by the agency. KS OS is responsible for ensuring each use is covered
  by the appropriate Envato licence.
- `GOOGLE_STITCH`: a design or template source. Stitch is not a separate
  production application and generated output is normalised into KS OS
  structured templates.
- `INTERNAL`: agency-owned templates.

A template manifest declares layouts, semantic page types, required sections,
conversion roles and approval status. Incompatible layout assignments are
rejected. Source packages do not become per-client production repositories.

## AI safety boundaries

- AI receives the minimum tenant context required for the generation job.
- Outputs must validate against strict structured schemas.
- AI cannot publish, configure domains, choose a different tenant, create an
  external booking destination, add scripts, or bypass entitlement and quality
  checks.
- Factual claims, contact details, services, locations and staff references
  remain subject to agency review and tenant ownership validation.
- Failed validation creates an auditable job failure; it does not silently fall
  back to unstructured HTML.

## Future infrastructure responsibilities

Provider adapters for Vercel, Cloudflare and IONOS will live behind publishing
and domain orchestration boundaries. They will receive server-held credentials,
idempotency keys and auditable jobs. Phase 15.0–15.2 adds no provider API calls,
credentials, projects, domains or deployments.
