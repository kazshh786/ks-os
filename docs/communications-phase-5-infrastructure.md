# Phase 5 media infrastructure review

This is an unapplied release plan. Application deployment is **BOTH VPS + CLOUDFLARE**. The new LiveKit media service is a separate, explicitly approved VPS infrastructure operation. No production migration, Docker installation, firewall change, DNS change, certificate change, service restart or media deployment is part of Phase 5 development.

## Evidence and unresolved prerequisites

Reviewed Phase 4 at commit `8327608a31a3eba84d5e9c9ed2998797857e6fe8` on 22 October 2026. The branch remains unmerged. The tracked deployment topology is `/srv/ks-os`, runtime user `ksdeploy`, Fastify API at loopback 5000, shared renderer at loopback 5001, website worker health at loopback 8091, and a communications systemd timer. Plesk/nginx manages origin TLS and vhosts. Cloudflare owns DNS and the web Worker. Tracked routes are `kasimshah.com/*` and `www.kasimshah.com/*`; the API origin is `https://api.kasimshah.com`. The older Cloudflare migration document also describes `app.kasimshah.com`; do not assume those records are the current authoritative zone state.

The repository contains no LiveKit, Docker Compose, Redis, Coturn or Nextcloud deployment inventory. Absence from Git is not evidence that those services are absent on the VPS. CPU, RAM, free storage, network quota, packet throughput, installed Docker, listening ports, firewall rules, existing Redis/Coturn, certificate renewal and monitoring resources have **not been measured**. Production infrastructure was not accessed during this audit. No production capacity is certified.

`scripts/deploy/livekit/inventory-readonly.sh` is an optional operator-run read-only inventory. It intentionally avoids environment contents, private keys and container configuration secrets. Also inspect the provider's bandwidth/transfer allowance, Plesk bindings and certificates, DNS records, network firewall, existing TURN realms/credential methods and monitoring. Record owners and listening addresses for TCP 80/443/7880/7881/5349 and UDP 3478/7882, 40000–40999, and any existing media ranges. Verify IPv6 too. If a permission check fails, obtain an operator inventory rather than assuming a port is free. No throughput load test against production is authorized by this plan.

GitHub's tracked production workflow only automatically follows successful main CI; manual dispatch is also production-capable. Phase 5 must never invoke it. Authenticated read-only Cloudflare dashboard verification on October 22 confirmed `ks-os-web` uses production branch `main`, enables builds for non-production branches, builds with `pnpm --filter web... build`, deploys production with `pnpm run deploy:cloudflare`, and runs the non-production Version command `pnpm run deploy:cloudflare:preview`. The latter resolves to `wrangler versions upload` in the reviewed repository and does not promote production. No deploy hooks were defined. No settings were changed. Feature-branch publication is compatible with the no-production-deployment constraint under these observed settings.

## Version pins and hosting choice

Use official packages and explicit versions: LiveKit Server `v1.13.10`, `livekit-server-sdk` `2.19.1`, `livekit-client` `2.23.0`. The React component package was evaluated; the implementation uses native KSOS React components with the official client SDK. These versions were verified against official release pages on October 22. Resolve the lockfile in GitHub and use frozen installs. Record the actual container digest in release evidence before production; do not silently replace a tag during an approved release. No Egress, Ingress, agent, transcription or recording services are required.

The review-only Compose example runs one isolated media container with host networking, bounded logs, a health check, restart policy and explicit CPU/memory caps. A single node does not require Redis; production multi-node operation should add a separately reviewed, isolated Redis service and failure plan. Never reuse an unrelated application's Redis without capacity, isolation and credential review.

The template's two CPU/two GiB container budget and eight-participant room ceiling are conservative *limits*, not a claim about available VPS resources or demonstrated capacity. Keep calling disabled until the operator reserves resources and measures the intended room/concurrency mix. Start with one room and the application's default four device connections per room; eight is a hard ceiling. Implemented camera defaults are 640×360 at 24fps with simulcast and adaptive subscriptions. Measure CPU, available RAM, inbound/outbound bandwidth, relay share, packet loss, join/reconnect latency and video decode performance before increasing any limit. Shared-host resource contention or incompatible listeners is grounds to recommend a dedicated media VPS; procurement is a separate approval.

## Proposed network topology

Do not run LiveKit's installation generator on the multi-service VPS. It installs infrastructure and takes over listeners which Plesk or another application may already own. The supplied configuration instead requires operator-approved paths and deliberately invalid placeholders until review.

1. Allocate an approved signalling hostname under the existing owned zone. Its exact name and address must be confirmed; none is created here. HTTPS/WSS on that address terminates at the managed reverse proxy and forwards only `/rtc` to LiveKit on `127.0.0.1:7880`.
2. Reserve a separate host-owned public IP for a separately approved TURN hostname. The embedded TURN server binds only this address on TCP 443 and UDP 3478, with a valid independently renewed certificate matching that hostname. Ensure the existing reverse proxy does not bind every interface on TCP 443. If this is impossible, use an operator-reviewed layer-4 SNI router or a dedicated media host/second address; do not replace Plesk or stop Coturn. UDP 443 is not taken by this template.
3. Permit direct ICE TCP 7881 and UDP 7882 on the media node. The UDP mux replaces a broad 50000–60000 range. Ensure configured/advertised `rtc.node_ip` is correct and routable, and verify NAT mappings. TURN relay ports 40000–40999 must not overlap another relay; review local/network firewall paths to the SFU rather than opening all ports indiscriminately.
4. Keep TCP 7880 and metrics TCP 6789 loopback-only. Administrative RoomService/Twirp is not public through the signalling vhost. Set server-only `LIVEKIT_API_URL=http://127.0.0.1:7880` when the KSOS API shares the media host. When KSOS and LiveKit are on different machines, provide an approved private, authenticated TLS network path and set `LIVEKIT_API_URL` to that endpoint. Public `LIVEKIT_URL` must not be reused to expose administrative routes.
5. Keep media/TURN DNS records DNS-only. Cloudflare's ordinary HTTP proxy is not a general UDP/TCP WebRTC relay. DNS-only signalling is the simplest initial path; proxied WSS requires a separate compatibility review and still does not carry media. Do not add a paid Spectrum dependency.
6. Preserve existing KSOS/Nextcloud/Coturn/Plesk listener assignments, firewall policy and certificate renewal. The example nginx file is review material, not a replacement Plesk configuration. A TURN service owned by Nextcloud cannot be assumed compatible: shared-secret authentication, ACLs, realm, permissions, quota and media ranges need specific review.

TCP 5349 is the usual TURN backend port when a network load balancer exposes TCP 443. Exposing 5349 alone does not provide the required restricted-network 443 fallback. The example directly reserves 443 on a separate address instead. Test forced TURN/TLS from a separate restricted network before claiming this connectivity works.

## Secrets, endpoint configuration and certificates

Application server variables are `LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET`, plus the implementation's bounded call configuration and private administration endpoint `LIVEKIT_API_URL`. Never use a `VITE_` prefix for secrets. `LIVEKIT_URL` is a public WSS endpoint returned only with an authorized room token; the API key/secret and `LIVEKIT_API_URL` stay on the server. Use distinct non-production keys for GitHub integration tests. The signed webhook route is `/api/v1/communications/conversations/meetings/webhook`.

Compose reads `LIVEKIT_CONFIG_FILE`, `LIVEKIT_KEYS_FILE`, and `LIVEKIT_TURN_CERT_DIR`; these are absolute file locations, not secret values. The key map lives outside the checkout, owned by the configured container UID and mode 0600. Config and certificate directories must allow only intended service access. Resolve `REPLACE_` placeholders in an operator-owned config copy, never in tracked examples. Match the webhook signing API key and endpoint to the implemented KSOS route before launch. Rotate credentials through coordinated server/API configuration; do not log key maps or join tokens.

Issue valid public certificates for approved signalling and TURN names and establish renewal ownership. TURN certificates are mounted read-only. Test a renewal and controlled reload/restart plan during a maintenance window; restarting the media node interrupts calls. Do not reuse Cloudflare Origin CA certificates for browser-direct WSS or TURN/TLS, because browser clients need a publicly trusted chain.

## Token and lifecycle constraints

The API must authenticate tenant/conversation membership for every operation and every join token. Use an opaque UUID room and per-join-session UUID identity, never an email, phone number or user-supplied room name. A new browser session gets a distinct identity, preventing one tab from disconnecting another; retries of the same pending join should reuse their server-owned session. Track multiple sessions separately from participant invitation state and derive attendance from observed joins/leaves.

Issue an explicit short TTL with only the exact room's join/publish/subscribe permissions and allowed media sources. No client token needs room creation, room administration, room listing, recording or ephemeral messaging grants. Keep `room.auto_create: false` so old tokens cannot recreate a deleted room, and keep remote unmute disabled.

Self-hosted LiveKit does not invalidate old tokens on removal. Connected clients receive refreshed tokens with at least a ten-minute validity window; a short original KSOS TTL is therefore **not** a guaranteed upper bound on rejoin. Deny replacement tokens, remove every unauthorized active session, verify eligibility again on participant webhooks and periodic room reconciliation, and document the residual exposure until old/refreshed tokens expire and reconciliation reacts. Stopping a KSOS session alone does not immediately stop its media connection.

Use the official `WebhookReceiver` with the original string body and Authorization header. The content type is `application/webhook+json`. Persist idempotency by event UUID, compare event time/room SID/session SID, and keep terminal meeting states terminal. `room_started` means the first participant joined, not merely `CreateRoom`; `participant_joined` observes established media. Webhook delivery is retried but not guaranteed. Reconcile participant/room snapshots and reconcile again after outages. Do not fabricate attendance duration for unobserved intervals; distinguish observed timestamps from estimates.

WebRTC transport encryption is not end-to-end encryption. No recording or third-party AI processing is enabled. End-to-end encryption would need a separate client key-distribution and compatibility design.

## GitHub-only media verification

Use a separate PR CI job on a hosted Linux runner, with no production environment, deployment credentials or production endpoint. Start the pinned LiveKit container using host networking and a temporary config scoped to loopback. Configure `rtc.node_ip: 127.0.0.1`, `use_external_ip: false`, `enable_loopback_candidate: true`, fixed test ports and `room.auto_create: false`. Use generated ephemeral test keys and a local webhook callback. Poll the local HTTP health check with a bounded timeout, print only redacted diagnostics, and always remove the container at job completion.

Run two isolated Playwright Chromium contexts against the real KSOS fixture and real LiveKit SDK. Fake camera/microphone devices are appropriate deterministic capture sources; use real RTCPeerConnections through LiveKit. Assert received RTP bytes and decoded frames grow, in addition to track subscription events. Assert audio samples/bytes arrive, camera mute/unmute, multiple sessions, participant removal and room termination. For screen-share transport, a canvas capture published as `ScreenShare` proves routing but not the browser picker. An actual `getDisplayMedia` call with Chromium's explicit automated capture flag provides browser capture-path evidence; still report that a human permission picker and physical/mobile devices remain unverified.

Test expired/wrong-room/wrong-signature tokens, no fresh tokens after membership removal, duplicate webhooks, a missing-webhook reconciliation path, network interruption/reconnection and post-end joins. Label browser media results separately from unit mocks and database/API tests. CI loopback success does not validate production DNS, TLS, NAT, TURN, external firewalls, restricted corporate networks, real microphones/speakers or mobile hardware.

## Release and rollback sequence

After explicit approval: record the exact application/media versions; back up and rehearse all pending communications migrations in an isolated environment; review the complete migration manifest and lock behavior; reserve media resources and listeners; establish DNS/TLS/firewall/private admin paths; install the reviewed Compose config; verify health, metrics and two-user media/forced TURN; configure the server variables; apply the approved additive database migrations; deploy the VPS API and Cloudflare frontend as one coordinated application release. The current automatic production path uses `APPLY_MIGRATIONS=0`, so it is insufficient for first release of the communications migration chain. Use the reviewed manual migration procedure, never schema push.

Monitor LiveKit process health, certificate expiry, CPU/RAM/network saturation, room/participant/track counts, connection quality, TURN allocations, KSOS join/token failures, webhook verification failures and reconciliation age. Metrics at loopback 6789 should be scraped by an approved local collector or private authenticated path; do not expose it publicly. Do not collect media or log tokens to diagnose incidents. An HTTP health check alone does not prove media connectivity.

Rollback first disables new call initiation, drains or explicitly ends active rooms, and restores the previous application/configuration release. Revert only the new approved DNS/firewall/proxy entries if necessary; preserve other services. Pin the previously verified media image/config. Database rollback uses a reviewed forward fix or separately restored database; do not automatically drop meeting/history tables. Preserve attendance and invitation audit records. Disabling calls does not remove LiveKit participants by itself.
